## The 25 questions

### 1. Architecture: what actually runs when you press go?

(a) Steelman. "A Python script posts to a chat channel and calls an API four times. Describe the system without the word agent."

(b) Answer. Fair. It is one Python runner, floor/round.py, and one client with two backends, a mock over seed JSON and an MCP client over Ambiguous. Pass one: three watchers each get a code-sliced view of one app and post FINDING cards to #agents-floor. Pass two: the Desk reads the cards, merges by account, posts PROBLEM cards, then for every action it posts ASSIGN, a code gate posts VERIFIER, and the worker posts DONE or BLOCKED. Then one brief to #attention with at most three items. Two passes, no loop, four model calls.

(c) Trap. Do not describe the four seats as four independent processes; it is one runner switching tokens.

(d) Evidence. Ambiguous, #agents-floor, the header posts "—— Round <date time> · pass 1 ——" and "—— Round <date time> · pass 2 · Desk merge ——" (the stamp is dt.datetime.now, round.py:1511); source floor/round.py:1507 run_round.

### 2. Why not one agent with all the tools?

(a) Steelman. "One Claude call with the CRM, mail, tasks and calendar in the prompt would find Pine & Salt faster and cheaper. The multi-agent split is theatre for the theme."

(b) Answer. One call would likely find the same problems on twenty deals. The split is not for accuracy. It is for evidence hygiene and blast radius. Each watcher's slice is cut in code, not by a prompt, and the router raises if a lane leaks a key. So Inbox cannot hallucinate a CRM fact and Ops cannot see a mail body. The Desk is the only place the lanes meet, and every write it proposes passes a gate that is code, not a model. That boundary is what I would keep at two thousand deals.

(c) Trap. Do not claim the split improves recall; the eval does not show that.

(d) Evidence. none live, source only, floor/router.py:52 slice_for and :75 the RuntimeError leak check.

### 3. Isn't this just Slackbots posting to each other?

(a) Steelman. "Every message on the floor is generated by the same script. Calling it multiplayer is a formatting choice."

(b) Answer. The channel is the audit trail, not the mechanism. Three things on the floor are not formatting. First, the FINDING cards come from three separately prompted model calls on three disjoint data slices. Second, the VERIFIER verdict is a code decision that can and does refuse the Desk. Third, a worker only executes after an approved verdict, and a BLOCKED receipt is real: on an empty inbox the draft chain ends in BLOCKED and nothing is written. If you strip the chat, you still have lanes, a gate and a three-item cap.

(c) Trap. Do not say the agents "talk to each other"; in pass one they cannot see each other at all.

(d) Evidence. Ambiguous, #agents-floor, one full chain "ASSIGN · Ops → add note", "VERIFIER · approved", "DONE · Ops · add_note"; source floor/round.py:1288 execute_actions.

### 6. What can it write, and how do I know it cannot go rogue?

(a) Steelman. "The Desk prompt lists crm.set_field and tasks.assign. A prompt injection or a bad merge could move a deal to Closed Won or reassign a person's work."

(b) Answer. Five verbs reach an app: add_note, draft, assign_task, ask, flag_event. That is the whole approved tuple. set_field is excluded from it, so no field can be set by the round, including safe-looking ones like amount. I tested that offline: an approved-looking set_field on amount, arr, probability and contact_id is refused and writes nothing. Drafts are drafts; the client has create_draft and nothing that sends. Calendar is read only; the client has list_events and no write. The prompt lists more verbs than the code allows, and the code wins.

(c) Trap. Do not read agents.yaml tool lists aloud as capabilities; they are aspirational, the tuple is real.

(d) Evidence. none live, source only, floor/round.py:1176 the approved tuple, :1360 execute-time field re-check, floor/client.py:28 to :43 the WorkspaceClient interface with no send and no calendar write.

### 7. Where is the MCP trust boundary? You trust whatever the server returns.

(a) Steelman. "Tool results are unwrapped and used as-is. A compromised or buggy MCP server could feed fake deals, fake mail, or fake channel ids and the agents would act on them."

(b) Answer. True, and I have not hardened it. The client sends a bearer token per agent, unwraps structured content or the first text block, and normalises deals and messages into the mock shape. There is no schema validation beyond that. The mitigation is downstream: whatever comes back can only produce five verbs, drafts never send, and the brief goes to humans before anyone acts on it. A poisoned CRM note would change what a note says, not which app gets written. Validating tool results is on the list, not done.

(c) Trap. Do not claim input validation you do not have.

(d) Evidence. none live, source only, floor/client.py:365 bearer header, :273 to :295 _unwrap_tool_result, :451 list_deals paged at 100.

## Never say

Each overclaim is paired with the sentence to say instead.

- Never say "the Verifier agent" or "the Closer". Say: "the VERIFIER verdict, which posts as Desk; there is no Verifier or Closer seat."
